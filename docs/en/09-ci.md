# Continuous integration

Status: **working** (2026-09-12).

The repository is public, so GitHub Actions minutes are free. The split into two
speeds therefore comes not from cost but from **response time**: nobody waits
eight minutes to have a typo checked.

## What runs when

| Run | When | Duration | What it checks |
|---|---|---|---|
| **Fast check** | every push, every branch | ~1–4 min | backend and frontend tests (**only those the change touches**), types, the production build, documentation consistency, task write-ups, syntax, PHPStan |
| **Full check** | every pull request and push to main **except text-only changes**, 03:17 UTC, manually | ~5 min | the full stack, the **Polish semantics test**, health through nginx, E2E against the production build, memory usage |
| **CodeQL** | on push and weekly | ~1 min | vulnerabilities in Python and the workflows; **AI findings** covers PHP |

### Scope of change — what runs and what does not

The `Zakres zmian` job compares the branch against `main` and emits two flags. A
change confined to the frontend does not wake Postgres, Composer or PHPStan; a
change confined to documentation wakes none of them.

| What changed | Backend tests | Frontend tests |
|---|---|---|
| `backend/`, `docker/backend/`, `docker/postgres/`, `plugin/` | yes | no |
| `frontend/`, `docker/frontend/`, `docker/nginx/` | no | yes |
| `docker-compose.yml`, `.github/workflows/`, `Makefile`, `.env.example` | yes | yes |
| `docs/`, `TODO/`, `CHANGELOG.md` | no | no |

Shared files land in **both** scopes, because they can break either side and
there is no way to say in advance which.

`plugin/` sits in the backend scope even though it holds no PHP at all: the
instruction content in `plugin/shared/` is what the gateway publishes as MCP
resources, and the backend tests compare a resource with the **real file**
(`docs/03-mcp-gateway.md`). Editing an instruction can therefore break PHPUnit, and
it has to do so on the branch rather than after the merge.

The comparison runs to the **merge base with `main`** (`git diff
origin/main...HEAD`), not to the file list of the latest push. A task branch
usually carries a dozen commits and it is the whole of it that counts —
otherwise a push fixing a typo would erase the fact that the backend was changed
ten commits earlier. On `main` there is nothing to compare against, so
everything runs.

No difference against `main` also runs everything. It should not happen, but
silently skipping every check would be worse than a wasted minute.

### Why there is no `pull_request` trigger

The fast check runs on `push` only — but on **every branch**. It used to be the
other way round, `branches: [main]` plus `pull_request`, and with a branch per
task that turned out to be wrong: pushing a task branch triggered nothing until
a pull request was opened, so the feedback vanished exactly when it is most
needed.

There is no second trigger because statuses attach to the **commit**: a run from
a push shows up in the pull request for the same SHA, and adding `pull_request`
would produce two identical runs for every change.

This has one consequence worth knowing: a pull request from a **fork** gets no
check here, and therefore cannot be merged. The direction is safe — blocked
rather than silently let through — and the trigger comes back if external
contributors ever appear.

### The frontend in the fast run

Four steps, each answering a different question: `pnpm typecheck` — will this build at
all, `pnpm test` — does it do what it should, `pnpm build` — is there a Vite
configuration error or a missing import in a lazily loaded component. The install uses
`--frozen-lockfile`, because a run resolving dependencies differently from the lockfile
is checking different code from the one that will ship.

The third step is sometimes the only one that catches anything: during TODO-006
`pnpm typecheck` passed while one file could not be parsed, and only the build revealed
a type error in an entirely different component. A check that quietly narrows its scope
when one file is broken is a check that lies.

## Why the fast run does not start the embedding server

Downloading the `bge-m3` model is about 2 GB and several minutes, and it checks
an assumption that changes once a quarter. Running it on every typo would turn
continuous integration into continuous waiting.

This required one change to the tests: `HealthTest` now checks the **contract** —
that every dependency is reported separately and the status code matches the
reported state — rather than whether the world happens to be up. "Does the whole
system come up" belongs to the full run, where the whole stack is standing.

The same principle governs the memory tests. `MemoryOnLivePalaceTest` **skips
itself** when the palace does not answer, so it is invisible in the fast run and
executes in the full one with no extra configuration — `make test` is the same
command in both. The permission rules, meanwhile, are covered by
`MemoryServiceTest`, without a database and without a palace, on every commit.

## Why the full run matters so much

It runs `test/semantyka.sh`, the only test guarding the assumption the entire
project rests on: **that a Polish query finds Polish content**. Breaking that
assumption is **silent** — search still answers, it just stops hitting. No
exception is thrown, no log lights up.

It therefore runs on **every** push to main and on every pull request. It used
to run only at night and on changes to a handful of files, because fetching the
model cost 2.3 GB every time. That was a consequence of a broken cache rather
than a law of nature; with the cache fixed, the full run finishes in a few
minutes, and there is no reason for the answer to "does this even come up" to
wait until morning.

The daily schedule stays, because it catches something a push cannot: an
external dependency breaking **without a commit of ours**. An image disappears
from a registry, a model stops being available, a release changes behaviour. A
run with no code change is the only way to see that in the morning rather than
at the next change — and to know that the next change was not to blame.

It also runs `MemoryOnLivePalaceTest` — the same chain, but through our
permissions: a Polish query in different words, a refusal for a stranger, a
drawer filed into our own wing past the registry. That test is what found that
MemPalace rejects an author label containing path characters and that the diary
answers with `entry_id` rather than `drawer_id` — no double would have shown
either.

It also records the services' memory usage. Not an assertion — a trace in the
run log. The embedding server once took 21 GB and choked the machine, so a
regular measurement will show it growing again.

## The integration tests clean up after themselves in the palace

The three classes in the `integracja` group — `MemoryOnLivePalaceTest`,
`McpOnLivePalaceTest` and `WikiOnLivePalaceTest` — write to a **real** palace, so
their `tearDown()` takes back everything they left there. This is not cosmetic:
on 2026-09-13 the server's palace held **over 1500 drawers**, of which **872
wings named `test-integracja-*`** and **128 orphaned `priv_<uuid>` wings** left
behind by test users. Real content: zero. It accumulated in a few days, because
every run wrote and nothing ever deleted.

The mechanism exists once, in the shared `RequiresLivePalace` trait, and rests on
two things that cannot be skipped:

- **Deleting the run's own wing is not enough.** Every run has its own
  `test-…-<hex>` wing, but a write that names no space lands in the author's
  private space (inviolable rule 6) — which is where those 128 `priv_<uuid>`
  wings came from.
- **`ws.memory_entries` is the register of what a run wrote.** It lists the
  drawers regardless of the wing they landed in, and in `tearDown` it is still
  intact: what clears it is the **next** test's `setUp`. `kg_fact` rows are
  skipped, because their identifier is derived from the fact itself and names no
  drawer. A drawer filed straight through the palace client, i.e. with no
  register row, is booked by the test explicitly (`alsoDeleteDrawer`).

Deletion goes through the palace's own API (`mempalace_delete_drawer`), never SQL
against the `palace` schema — D-004 covers tests as well. Rationale: **D-037**.

A cleanup failure **never fails the test** — a palace that stopped answering at
the end of a run says nothing about the code under test — but it is printed on
stderr together with the wing's name. A silent cleanup failure is precisely the
mechanism that produced the thousand wings above, so it must not be muted.

The check is single and measurable: `mempalace_status` before the group's run and
after it must report the **same** `total_drawers`.

## E2E runs against the production build, not the dev server

The end-to-end tests bring the frontend up with `FRONTEND_TARGET=prod`: static
`dist/` served by nginx. The first reason is obvious — that is the artefact that
actually ships, so that is what the tests should exercise.

The second reason cost two red runs and is worth recording. The dev server
pre-bundles dependencies on the fly. The `@codemirror/*` packages and
`markdown-it` are imported only by the editor screen, so Vite discovered them
when that screen was first opened, re-bundled, changed the hash in module URLs —
and requests already in flight were answered `504 Outdated Optimize Dep`. The
dynamic import rejected and the editor screen was **blank**: no error, no
layout, nothing.

The crucial part: **it does not reproduce on a developer's machine.** Clearing
Vite's cache and starting the container cold came out green every time, because
the start-up scan won a race that it loses on the runner. The red light burned
only in CI, and only there could it be investigated — through the Playwright
trace, which named exactly six requests and their status codes.

A production build has no optimiser, so the problem disappears at the source.
Two fixes made along the way were kept, because both are worth having outside
CI: `optimizeDeps.include` (so a developer does not meet the same thing) and
`router.onError`, which reloads a page once when its code fails to load. That
second one is about **production**: after a deployment somebody has the old page
open and asks for a file that is gone — until now they would have seen a blank
sheet.

Building the image is a check in its own right, since it runs `vue-tsc`: a type
that does not fit stops the run instead of shipping.

## When the full check does not happen

A change confined to text (`docs/`, `TODO/`, any `.md`) does not stand the stack
up, because there is nothing for it to break. Writing up TODO-016 changed two
text files and cost the full run 4 min 57 s — pure waste.

The path filter sits at the **workflow** level rather than the job level, and
that is safe **only because** the full check is not a required check. If it were,
a skip would not report as green but as permanently pending — and would block
every documentation pull request. The only required check is `Wynik sprawdzenia`
from the fast run. Changing this list, or the protection rule, means checking
both places together.

The push script waits for **all** of a pull request's checks, so the full check
still has to be green before a merge — even without the ruleset requiring it.

## Model weights between runs

The model is about 2.3 GB and the full run needs it every time.
`actions/cache` can remember **a directory on the runner** — and nothing else. A
Docker named volume, which is where the embedding server keeps the weights by
default, is invisible to it.

So the `embeddings` service takes its path from `EMBEDDING_CACHE_DIR`. On a
developer's machine the variable is unset and the named volume stays — nobody
wants 2.3 GB inside the project directory. The full run points it at a host
directory, which is then what the cache covers.

The cache key contains the model name **read from `.env.example`** rather than
written by hand. Changing the model then invalidates the weights along with the
vectors (D-003), instead of checking Polish semantics against the previous
model's weights.

How this came to light is worth knowing, because there was no symptom. The cache
step had been there from the start and looked right: it pointed at
`/tmp/model-embeddingow`, it had a key, it raised nothing. The model simply never
went there, so the step saved an **empty directory** — and an empty directory has
nothing to restore and nothing to complain about. Every run downloaded 2.3 GB and
nobody saw it, because nobody measured. It shows up only in the repository's
cache listing (`gh api repos/:owner/:repo/actions/caches`): of 46 entries, not
one was for the embeddings.

Fixing the path was **not enough**, and the second reason is the more
interesting one. `actions/cache` saves in a post step, and **only when the whole
job succeeded**. Ours was failing on the E2E tests, so the save never happened —
the log shows `save-always: false` and no "Post Cache" step at all.

That is a trap that feeds itself: **one red test blocks the cache forever**, and
every subsequent run downloads 2.3 GB again. The longer one thing stays broken,
the more expensive it becomes to fix anything else.

So restore and save are split (`cache/restore` + `cache/save`), and the save
carries `if: always()`. Not unconditionally, though: it is gated on the
**semantics test** passing, because only that proves the model loaded in full.
Saving the cache after an interrupted download would freeze corrupt files under
the same key and break every run after it — turning one bad run into a series.

The lesson is double. **A cache step that never hits looks exactly like a cache
step that works** — the only proof is the cache listing, or the run's duration.
And: **check when a tool saves, not merely whether you configured it right.**

## Three legs of code scanning (D-018)

**CodeQL does not support PHP.** With nothing else, the Symfony backend would be
invisible to scanning. Hence three complementary tools:

- **CodeQL** (default setup, repository settings) — Python and the workflows.
- **AI findings** — security findings for PHP. A preview feature and
  non-deterministic: **a prompt to review, not a gate**.
- **PHPStan level 8** — correctness bugs no vulnerability scanner will report.
  A permission rule that always returns true is not a vulnerability, it is a
  quietly opened door.

CodeQL runs in **default setup** rather than a custom workflow file, because AI
findings requires it and the two modes are mutually exclusive.

## Protecting the main branch

A ruleset named **Ochrona gałęzi głównej** guards `main`:

| Rule | Why |
|---|---|
| branch deletion forbidden | obvious, and costs one click |
| force pushes forbidden | the same thing `AGENTS.md` states — now enforced rather than merely promised |
| `Wynik sprawdzenia` must pass | a red run cannot reach `main` |
| pull request required (zero approvals) | a PR is the default route, but one-person work need not review itself |

**One** job is required rather than three, and that is deliberate — D-031
explains why. In short: checks are narrowed by path, and a skipped job does not
report as green but as permanently pending. Requiring them directly would block
every pull request they happen not to concern.

**Administrators can still bypass the rules — and do not.** The exception stays
as a safety valve for the case where a required check breaks for good and blocks
everything. For a while, though, it was used routinely: the push script pushed
straight to `main`, and its output said so on every commit —
`Bypassed rule violations for refs/heads/main`. A rule bypassed on every use
protects nothing, which is why since D-031 the route runs through a task branch
and a pull request.

The force-push ban carries double weight here: we used exactly such a rewrite
once, deliberately, to anonymise client names. From now on that requires
disabling the rule — a decision rather than a reflex.

## Dependabot

Three ecosystems, with updates **grouped**: PHP packages (Symfony, Doctrine and
dev tooling separately), GitHub actions, Docker images.

Grouping is not cosmetic. Twenty separate pull requests a week go unreviewed,
and unreviewed PRs are **worse than none** — they create the impression that
somebody is on top of it.

Deliberately excluded from automation:

- **major Symfony and Doctrine versions** — that is a migration, not an update;
- **major Postgres versions** — `pg_upgrade` and a maintenance window, not a
  merged PR.

The first run showed immediately what this is all for: Dependabot proposed
bumping Python in the memory image from 3.12 to 3.14. **The full run executed
the semantics test on that branch**, and only its result justified the merge.
Without that gate it would have been a leap in the dark — and the failure would
have surfaced quietly, as worse search results.

## The wiki as a rendered mirror

The GitHub wiki is **generated** from `docs/` by the **Publikacja wiki**
workflow, which runs after every merge to `main` that touched documentation.

It is not a second source of truth and cannot become one. A manual edit to a
page will be overwritten at the next publication, and every page says so in its
header. Content is written in the repository, where it goes through pull request
review and the consistency check across both language versions.

**Why not the other way round:** the wiki is a separate repository. CI, the
ruleset and change review do not cover it, and a change there cannot sit in the
same commit as the code it describes — which breaks the first point of the
definition of done.

The generator (`scripts/zbuduj-wiki.py`) rewrites links from file paths to wiki
page names. Without that every link would lead nowhere, and documentation you
cannot click through stops being read.

Local preview without publishing: `make wiki`.

**One manual step, once:** GitHub creates the wiki repository only after the
first page is saved through the interface, and there is no API for it. The
workflow reports this with a readable message instead of failing on a git error.

## What to do when a run is red

**Backend tests.** Reproduce locally: `make start && make test`. CI uses the same
database and the same migrations, so a difference usually means state left in
the local database — the tests truncate tables in `setUp` but do not undo
earlier migrations.

**Documentation consistency.** `make sprawdz-dokumentacje` says exactly what is
missing. Most often: a change in `docs/` without its counterpart in `docs/en/`.

**Task write-ups.** `make sprawdz-zadania`. Most often: a task marked complete
but still outside `TODO/DONE/`.

**PHPStan.** `make analiza`. We do not lower the level to get green — level 8 was
reachable from the first run and is to stay that way. If a report is a false
positive, add an exception with a comment saying **why**, rather than silencing
the whole rule.

**The full run.** First check it is not a model download failure (Hugging Face
is occasionally unavailable). If the semantics test genuinely failed, check
`MEMPALACE_EMBEDDING_MODEL` and the model in the `embeddings` service — those are
the only two settings that can ruin relevance with no other symptom.

## What we deliberately do not do

**A self-hosted runner.** It would make the full run nearly free, with the
model sitting on disk. With a **public** repository, though, it is a serious
hole: anyone can open a pull request, and the runner would execute the code it
carries on our machine.

**Gating merges on AI findings.** A non-deterministic result makes a poor
condition — it would pass and block the same code on different days.

**Building images on every push.** That arrives when there is somewhere to
deploy to.
