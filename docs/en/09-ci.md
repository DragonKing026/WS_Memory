# Continuous integration

Status: **working** (2026-09-12).

The repository is public, so GitHub Actions minutes are free. The split into two
speeds therefore comes not from cost but from **response time**: nobody waits
eight minutes to have a typo checked.

## What runs when

| Run | When | Duration | What it checks |
|---|---|---|---|
| **Fast check** | every push and pull request | ~3 min | backend tests, documentation consistency, task write-ups, syntax, PHPStan |
| **Nightly check** | 03:17 UTC, manually, and on embedding-configuration changes | ~10 min | the full stack, the **Polish semantics test**, health through nginx, memory usage |
| **CodeQL** | on push and weekly | ~1 min | vulnerabilities in Python and the workflows; **AI findings** covers PHP |

## Why the fast run does not start the embedding server

Downloading the `bge-m3` model is about 2 GB and several minutes, and it checks
an assumption that changes once a quarter. Running it on every typo would turn
continuous integration into continuous waiting.

This required one change to the tests: `HealthTest` now checks the **contract** —
that every dependency is reported separately and the status code matches the
reported state — rather than whether the world happens to be up. "Does the whole
system come up" belongs to the nightly run, where the full stack is standing.

## Why the nightly run matters so much

It runs `test/semantyka.sh`, the only test guarding the assumption the entire
project rests on: **that a Polish query finds Polish content**. Breaking that
assumption is **silent** — search still answers, it just stops hitting. No
exception is thrown, no log lights up.

That is why this run also fires **immediately** on changes to
`docker-compose.yml`, the memory image or `.env.example`: those are the only
places where relevance can be broken quietly, and they must not wait for the
next night.

It also records the services' memory usage. Not an assertion — a trace in the
run log. The embedding server once took 21 GB and choked the machine, so a
regular measurement will show it growing again.

## Three legs of code scanning (D-018)

**CodeQL does not support PHP.** With nothing else, the Symfony backend would be
invisible to scanning. Hence three complementary tools:

- **CodeQL** (default setup, repository settings) — Python and the workflows.
- **AI findings** — security findings for PHP. A preview feature and
  non-deterministic: **a prompt to review, not a gate**.
- **PHPStan level 8** — correctness bugs no vulnerability scanner will report.
  A permission rule that always returns true is not a vulnerability, it is a
  quietly opened door.

CodeQL runs in **default setup** rather than a custom workflow file, because AI
findings requires it and the two modes are mutually exclusive.

## Protecting the main branch

A ruleset named **Ochrona gałęzi głównej** guards `main`:

| Rule | Why |
|---|---|
| branch deletion forbidden | obvious, and costs one click |
| force pushes forbidden | the same thing `AGENTS.md` states — now enforced rather than merely promised |
| `Testy backendu` and `Dokumentacja i zadania` must pass | a red run cannot reach `main` |
| pull request required (zero approvals) | a PR is the default route, but one-person work need not review itself |

**Administrators bypass the rules.** A deliberate compromise: with one person
and an assistant, forcing a pull request for every documentation typo would be
ceremony without substance. Once more people join, removing the exception is
enough — the rules are already in place.

The force-push ban carries double weight here: we used exactly such a rewrite
once, deliberately, to anonymise client names. From now on that requires
disabling the rule — a decision rather than a reflex.

## Dependabot

Three ecosystems, with updates **grouped**: PHP packages (Symfony, Doctrine and
dev tooling separately), GitHub actions, Docker images.

Grouping is not cosmetic. Twenty separate pull requests a week go unreviewed,
and unreviewed PRs are **worse than none** — they create the impression that
somebody is on top of it.

Deliberately excluded from automation:

- **major Symfony and Doctrine versions** — that is a migration, not an update;
- **major Postgres versions** — `pg_upgrade` and a maintenance window, not a
  merged PR.

The first run showed immediately what this is all for: Dependabot proposed
bumping Python in the memory image from 3.12 to 3.14. **The nightly run executed
the semantics test on that branch**, and only its result justified the merge.
Without that gate it would have been a leap in the dark — and the failure would
have surfaced quietly, as worse search results.

## What to do when a run is red

**Backend tests.** Reproduce locally: `make start && make test`. CI uses the same
database and the same migrations, so a difference usually means state left in
the local database — the tests truncate tables in `setUp` but do not undo
earlier migrations.

**Documentation consistency.** `make sprawdz-dokumentacje` says exactly what is
missing. Most often: a change in `docs/` without its counterpart in `docs/en/`.

**Task write-ups.** `make sprawdz-zadania`. Most often: a task marked complete
but still outside `TODO/DONE/`.

**PHPStan.** `make analiza`. We do not lower the level to get green — level 8 was
reachable from the first run and is to stay that way. If a report is a false
positive, add an exception with a comment saying **why**, rather than silencing
the whole rule.

**The nightly run.** First check it is not a model download failure (Hugging Face
is occasionally unavailable). If the semantics test genuinely failed, check
`MEMPALACE_EMBEDDING_MODEL` and the model in the `embeddings` service — those are
the only two settings that can ruin relevance with no other symptom.

## What we deliberately do not do

**A self-hosted runner.** It would make the nightly run nearly free, with the
model sitting on disk. With a **public** repository, though, it is a serious
hole: anyone can open a pull request, and the runner would execute the code it
carries on our machine.

**Gating merges on AI findings.** A non-deterministic result makes a poor
condition — it would pass and block the same code on different days.

**Building images on every push.** That arrives when there is somewhere to
deploy to.
